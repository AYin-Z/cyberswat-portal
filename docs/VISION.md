# CyberSWAT 数字化中枢 — Meta 愿景与迭代路线图

> 日期：2026-08-15 · 状态：愿景 v1.4（2026-08-15 四次评审：scope 权限点级 / core_agents / AI 署名 / 三客户端验证）
> 定位：从"一个开发部子站"到"整个队伍的数字化基础设施"的顶层构想与演进路径

## 1. Meta 愿景（一句话）

> **CyberSWAT 数字化中枢：一个把"对外展示、对内协作、智能辅助、代际传承"四层打通的平台。**
> 每个部门有自己的子站（展示+协作），每个部门有一个 agent（智能），
> 每一届成员在系统里留下作品与轨迹（传承），招新从"进群"变成"进系统"。

## 2. 四层架构

```
┌─────────────────────────────────────────────────────────┐
│ L4 传承层   招新漏斗 · 成长档案 · 换届交接 · 组织记忆        │  ← 长期
├─────────────────────────────────────────────────────────┤
│ L3 智能层   部门 agent（每个部门一个）· 工具注册表统一暴露    │  ← 中期
│            · 事件驱动主动服务 · 审批+审计兜底               │
├─────────────────────────────────────────────────────────┤
│ L2 协作层   子站体系（8 部门）· 公告/任务/点子/社区/项目     │  ← 当前
│            插件化内核可复制 · 开发部已上线（样板）           │
├─────────────────────────────────────────────────────────┤
│ L1 展示层   cyberswat.cn 主站（✅）· 部门子站域名入口       │  ← 已就绪
└─────────────────────────────────────────────────────────┘
```

**分层原则**：上层依赖下层接口，下层不感知上层。L2 的插件化内核（能力包/manifest/工具注册表）是 L3 智能层的底座——agent 之所以"自然长出"，是因为工具、权限、审计、事件在 L2 已经是第一公民。

## 3. 愿景支柱（每个支柱回答一个"为什么"）

### 支柱 A：子站体系 = 可复制的组织能力（L2）
- 开发部子站是样板，不是终点。attack/forensics/modeling/algorithm/bigdata/ai/pr 各自提 PRD，
  复用内核（认证/权限/通知/工具注册表），只写自己的能力包
- 复制成本目标：一个新部门子站 = 1 个能力包 + 1 套部署配置，而不是重写一套系统

### 支柱 B：部门 agent = 队伍的 AI 队友（L3）
- 每个部门一个 agent：攻防部 agent 懂 CTF 赛程与荣誉、开发部 agent 懂项目人力、宣传 agent 懂内容排期
- agent 是"特殊成员"：有身份（bot:*）、有权限（tools 白名单 + 审批）、有记忆（事件订阅）、有产出（草稿态）
- 关键纪律不变：写操作一律审批 + 全量审计（公安院校场景是红线）

### 支柱 C：传承 = 系统的隐藏价值（L4）
- 换届最怕"人走经验走"。系统里沉淀：项目/点子演进、任务流转、社区问答、成员成长轨迹
- 招新从"微信群里喊人"变成"系统里一条完整漏斗"：注册（邀请制）→ 资料 → 项目参与 → 贡献轨迹 → 留任
- 成员主页就是"活简历"：Vidar 卡片 + 项目经历 + 社区贡献，毕业时一键导出

### 支柱 E：AI 友好 = 系统是一等 MCP Server（2026-08-15 新增，用户拍板）
- **愿景升级**：未来人手一个 agent（成员自己的 AI 助手），系统必须能被任何 agent 接入——
  不只是内置部门 bot，而是"成员 agent 的服务提供方"
- **形态**：系统暴露标准 MCP Server 端点（官方 @modelcontextprotocol/sdk），
  全量工具自动暴露（注册表即暴露面，requiresApproval 自动生效）
- **认证**：OAuth 2.1 + PKCE + **RFC 7591 动态客户端注册**（主流 MCP 客户端标准接入方式；
  参考 hermes mcp-oauth-remote-gateway 经验，GitHub 类不支持 DCR 的服务才用 PAT 例外）
- **授权模型**：agent 权限 = 其主人（成员）权限的继承 + requiresApproval 审批兜底 +
  全量审计（ToolCallRecord.agentId 第一版已预留）
- **数据面**：member 级脱敏面（已拍板）——agent 上下文永不出现真实姓名/区队
- **插件封装**：/agent 接入页（工具清单 + Claude/Cursor/Codex 配置片段 + 授权入口）
- 与 DSH 哲学呼应：dsh-mcp-client 把外部 server 注册进 ctx.tools，我们做对称面——
  系统是 Server，成员的 agent 是 Client，同一 ToolRegistry 双面复用

### 支柱 D：安全与隐私 = 前提不是功能（贯穿）
- 公安院校：姓名/区队/联系方式永不公开，脱敏在 API 层统一做（已实现）
- agent 永不越权：工具级权限点 + 审批 + 审计（已实现）
- 生产凭证、OAuth 密钥管理纳入迭代必做项

## 4. 迭代路线图

| 迭代 | 名称 | 目标 | 关键交付 | 验收标准 |
|---|---|---|---|---|
| **R1** | 成员体验打磨 | 让"进来的人留得下" | 个人资料编辑页 · 成员主页项目经历 · 通知中心完整 UI · 生产凭证更换 | 成员能维护自己的资料；线上无 dev 凭证 |
| **R2** | agent v0 上线 | 第一个 AI 队友进系统 | MCP 端点（官方 SDK+JWT）· 开发部 agent（后台型）· 审批工作台 · 招新页 | agent 能订阅事件、调用工具、产出草稿待审批；部长能在工作台处理 |
| **R3** | 子站体系复制 | 验证"复制骨架"流程 | 攻防部子站 attack.cyberswat.cn（第二个样板）· 子站脚手架文档 | 第二个部门子站从零到上线 ≤ 原开发部耗时的 1/3 |
| **R4** | 智能深化 | agent 体系化 | 多部门 agent · 跨部门事件协同（如点子跨部门转交）· 知识沉淀（Wiki 雏形） | 至少 2 个部门 agent 同时在线协作 |
| **R5** | 传承生态 | 系统成为组织记忆 | 招新漏斗完整化 · 成员成长档案/贡献轨迹 · 换届交接包 | 换届时能导出完整交接文档；招新全流程在系统内完成 |

**节奏**：每轮迭代含 安全必做项（凭证/审计复核）。R1-R2 聚焦开发部（当前唯一在运营的部门），R3 起验证横向复制。

## 5. 不做清单（边界纪律）

- ❌ 不做完整社交网络（私信/关注/时间流）——轻量社区已够
- ❌ 不做 OA/审批流引擎——任务闭环到"验收"为止，agent 审批走轻量工作台
- ❌ 不做多租户 SaaS 化——子站是"复制部署"不是"一库多租"
- ❌ 不引入消息队列/微服务——单容器小规模，进程内事件总线够用（L2 纪律延续）

## 6. 与主站的关系

- 主站 cyberswat.cn = 展示层入口（部门总览 → 跳子站）
- 子站 = 协作层（登录、数据、agent）
- 主站不承担登录/数据（保持纯静态，安全面最小）
- 后续：主站"部门风采"数据可由子站导出（脱敏后），或主站做只读聚合

## 7. 评审结论（2026-08-15 用户拍板）

1. **agent 形态**：✅ 双轨制——① 系统内置 bot（社区嵌入式 C 型，@ 触发，天然可审计）；
   ② 成员自己的 agent 经 MCP Server 端点接入（OAuth 2.1 + DCR，R2 一并上线）；
   后台管家型（A）紧随，前台对话型（B）等价值验证后再说
2. **R1 优先级**：✅ 人力匹配优先——成员技能资料 + 点子匹配通知先行
   （关键联动：技能标签按"给 agent 吃"的结构化标准设计，R1 资料页是 R2 agent 的知识源）
3. **agent 数据面**：✅ member 级脱敏面——agent 只见昵称/技能/签名，真实姓名/区队/联系方式
   永不进 agent 上下文（AI 是最大泄露通道，保守优先）
4. **子站策略**：✅ 严格等 PRD——只维护 dev，其余部门按既定原则"部门自己提 PRD"再启动
   （愿景的"8 站全量"降级为"PRD 驱动"）

## 7.5 安全缝隙裁决（2026-08-15 压力测试，用户拍板）

1. **聚合攻击防护**：✅ 双限额 + 聚合视图——读限额 30 次/时、写限额 5 次/时（超限进审批），
   全部挂在 ToolRegistry（零架构改动）；审计聚合视图（某 agent 时间窗内工具调用与聚合内容）部长可见
2. **OAuth 授权粒度**：✅ 现在就做 scope——scope ↔ 权限点映射，授权页按能力包分组勾选，
   access token 携带 scope 声明，工具调用校验 scope ⊆ token（R2 工作量 +30%）
3. **技能词表**：✅ 两级词表——分类（Web前端/后端/数据库/安全/算法/AI/运维…）→ 技术（Vue/NestJS/PostgreSQL…）；
   匹配用技术级，展示用分类级；词表开放加词后治理
4. **生命周期**：✅ 级联撤销——冻结用户 → 撤销其 refresh token（core_refresh_tokens 按 userId 级联）；
   DCR client 保留（无有效 token 即废）；bot 归 admin 管理（换届交接 bot 人格配置）

## 7.6 第二轮缝隙裁决（2026-08-15，用户拍板）

5. **scope 粒度**：✅ 权限点级（最细）——授权页展示全部权限点（含描述）逐项勾选，
   需设计默认值（倾向：只读权限点默认勾选，写权限默认不勾）避免"全勾失去意义"；
   token scope = 权限点 id 列表，工具调用校验 requiredPermission ∈ token scope
6. **bot 配置存储**：✅ 建 core_agents 表——name/persona/身份 bot:* / 工具白名单覆盖 / 启用状态；
   内置 bot 是首行数据，未来部门 bot 同表扩展（插件化一致）
7. **AI 代发标识**：✅ 写操作落 authorViaAgent 字段（工具上下文 via_agent 标志），
   前端帖子/点子显示 "🤖 AI 代发" 角标（合规 + 诚实原则，公安院校内容管理基本要求）
8. **验证策略**：✅ 三客户端交叉验证——官方 inspector + Claude Desktop + hermes
   （真实 DCR + loopback 流程实测），全过才算 R2-B DoD

## 8. 遗留讨论项（不影响当前迭代）

1. 招新注册：独立域名（reg.cyberswat.cn）vs 子站内嵌页——R3 前定
2. 知识沉淀载体：自建 Wiki 能力包 vs 外链——R4 前定
3. 子站公开性：全部公开 vs 部分内网——随 PRD 逐站评估
4. 社区 agent 触发范围：@ 起步 → HELP 板块自动响应（R2 时定）
