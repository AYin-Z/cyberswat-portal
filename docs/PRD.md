## 4. 构思池（用户逐条补充，每条记录：构思 / 背景 / 问题点 / 评审结论）

### 构思 #1 — 用户权限系统（2026-08-06）
- **构思**：公网访客只能看到公布的信息；网特成员登录账号后可以参与系统。不是静态站，是前后端完备项目。
- **背景**：门户需要区分"对外展示"与"对内协作"两个面。
- **问题点**：
  - 认证方式待定（自建账号 / GitHub OAuth / 学校统一认证）
  - 成员账号生命周期（招新→开号→换届→毕业）谁管理
  - 公安院校学生隐私敏感：区队/真实姓名对外展示需谨慎
  - 角色粒度：访客/成员/管理员，是否部门级隔离
- **评审结论**：✅ 已拍板（2026-08-06）
  - **认证：邮箱为主**（人人有，公安院校成员不都有 GitHub），**GitHub OAuth 为二级认证**（可选绑定：一键登录 + 成员主页 GitHub 信息自动同步）
  - 账号激活：邀请制（管理员/部长开号 or 注册后审核）——GitHub 无法证明网特身份，邮箱注册也必须审核

### 构思 #2 — 开发部子站先行（2026-08-06）
- **构思**：先设计开发部子站（用户现任开发部部长）。开发部成员主页：过往项目经历、个人信息、GitHub 主页跳转。开发部子站主页：公告、招人的项目信息、人力需求、成员点子（正缺人手）。核心目标：极大强化开发部内信息交流效率。
- **背景**：开发部是用户直接负责的部门，需求最清晰；作为子站体系第一个样板。
- **问题点**：
  - 成员主页数据模型（个人信息/项目/技能/GitHub）
  - 公告/项目/点子三块内容的发布与权限（部长发布？成员可发？）
  - "点子→人力"连接机制（缺人项目如何匹配成员）
  - 交流机制深度：评论/点赞/通知，还是仅信息发布？
- **评审结论**：TBD（成员主页外链已补充：个人简介区可放 Blog 站链接，见下方数据模型）

### 构思 #3 — 成员主页外链区（2026-08-06）
- **构思**：个人简介那里可以放自己的 blog 站。
- **背景**：技术成员普遍有个人博客/站点（Vidar 成员页大量外链个人站），是展示技术积累的重要入口。
- **设计**：成员主页外链区支持**多个链接**：GitHub（OAuth 绑定自动带出）+ Blog 自定义 + 其他（掘金/博客园/知乎等），每个带 label + url。数据模型 users.links: [{label, url}]。
- **评审结论**：✅ 采纳，与 Vidar 成员卡外链模式一致；GitHub 自动同步，Blog 手动填。

### 构思 #4 — 点子墙（2026-08-12，用户称为"电子墙"）
- **构思**：有人有好点子，但缺人力/物力/技术力去实现 → 发布点子，招募成员一起做项目。
- **背景**：灵感来自"电子墙"概念，落到开发部场景即"点子→人力"连接机制（构思 #2 的待评审问题之一）。
- **问题点**：
  - 点子的生命周期：点子 → 讨论 → 认领 → 转正为正式项目（关联构思 #5 的孵化机制）
  - 点子与项目的边界：什么时候算"项目"而不是"点子"（人力/技术评估通过后？）
  - 点子发布权限：所有成员可发？还是要部长审核？点子墙是否区分"求助技术力"与"求助人力"两类？
- **评审结论**：✅ 采纳为开发部子站核心功能之一。数据模型与"项目广场"同源（OSPP 卡片模板），点子 = 未转正项目，字段比正式项目少（无产出要求/工时），核心字段：标题/描述/缺什么（人力/技术/资源）/技术栈/发起人/状态。

### 构思 #5 — 信息流转体系（2026-08-12）
- **构思**：公告 → 已读追踪（谁看了没看，重要公告需确认）；任务分派流转（指派→接单→提交→验收）；点子 → 项目孵化。
- **背景**：开发部内信息流通效率是子站核心目标（构思 #2），三件套覆盖"上情下达（公告）→ 任务执行（分派）→ 自下而上创新（点子孵化）"完整闭环。
- **问题点**：
  - 公告已读追踪粒度：仅"已读/未读"还是需要"确认收到"？超时未读是否二次提醒？
  - 任务分派：是否需要截止时间/优先级/催办？与点子/项目的关系（任务挂在项目下？）
  - 通知渠道：站内通知必然，是否邮件/微信/公众号推送？
- **评审结论**：✅ 采纳三件套全做，分阶段：M1 公告已读追踪 → M2 任务分派 → M3 点子孵化。通知 MVP 阶段仅站内（轮询/SSE），邮件二期。

### 构思 #6 — 轻量成员社区（2026-08-12）
- **构思**：帖子 + 评论 + 点赞 + @通知，类似内部论坛，先跑起来。
- **背景**：构思 #2 末尾"交流机制深度：评论/点赞/通知，还是仅信息发布？"的评审结论。
- **问题点**：
  - 社区帖子是否需要板块（灌水/求助/分享/招人）？还是单一信息流？
  - 与点子墙/公告的边界：社区帖子是"讨论"，点子墙是"招募"，公告是"官方信息"——是否允许互相转化/关联（帖子可"转点子"）？
  - 权限：社区对公网访客是否可见？还是仅成员？
- **评审结论**：✅ 采纳为轻量社区（不引入私信/关注/完整通知中心）。公网访客可见帖子列表但不可发帖/评论（延续"静态展示层公开 + 协作层登录"原则）。帖子按板块分类，支持"转点子"动作衔接点子墙。

### 构思 #7 — 后端技术选型（2026-08-12）
- **分析**：docs/tech-stack-analysis.md
- **结论**：✅ 已拍板并落地（2026-08-12 拍板，2026-08-15 全功能上线）
  - **API**：NestJS 11（TS）+ JWT + GitHub OAuth；**ORM**：Prisma；**DB**：PostgreSQL 16；**实时**：socket.io；**前端**：Vue3 + Vite + TS + Pinia（与主站同栈）
  - 核心理由：全栈单一 TS 语言类型全链路共享 + Guard 权限/脱敏体系 + 模块化可复制给其余 7 个部门子站 + 社团新人易接手
- **仓库组织**：✅ 独立仓库 `cyberswat-dev-portal`（个人 + 组织双仓推送），pnpm workspace monorepo（apps/web + apps/api + packages/shared），理由见选型文档 §5

### 构思 #8 — 插件化架构 + 部门 agent 路线（2026-08-12）
- **构思**：借鉴 DSH（Cordis 内核）"一切皆插件"设计哲学：内核极简 + 能力包（公告/点子墙/社区/任务）= 插件 + 五个扩展点（事件总线/工具注册表/UI贡献/权限点/数据模型）。未来部门 agent 以插件形态接入。
- **调研**：docs/plugin-architecture-eval.md（DSH 源码一手证据 + 外部生态检索）
- **评审结论**：✅ 已认可并落地（2026-08-12 认可 → 2026-08-15 全功能上线，L0 代码级插件全部实现）
  - 五个扩展点：EventBus（@nestjs/event-emitter，进程内）+ ToolRegistry（JSON Schema 校验 + 权限点 + 审计，MCP 官方 SDK 暴露）+ 权限点 Decorator（RBAC 角色 + 细粒度权限点）+ 前端 manifest 静态合并（**禁运行时加载**）+ 数据模型命名空间规范（**不用合并工具**）
  - 部门 agent = 特殊插件：persona + tools 白名单 + 事件订阅 + `bot:*` 身份；**写操作一律草稿态审批 + 审计**；MVP 只做后台 agent，前台交互 L2
  - 纪律：L0 锁定代码级插件（NestJS Module + manifest.ts），禁提前上运行时加载/消息队列/微前端；L1 配置驱动启停 + MCP 端点 + agent v0；L2 条件触发（独立插件仓库/热加载）
  - 最大风险：抽象过度 + Prisma 多 schema 生态盲区（以命名空间规范规避）

## 5. 调研：同类项目参考（2026-08-06）

### 5.1 Vidar-Team（杭州电子科技大学）— 最直接的同类参考
官网 https://vidar.club 结构：HOME / ABOUT / MEMBER / GLORY + Wiki + Join us
- **MEMBER 页**（核心借鉴）：成员卡片 = 头像 + 昵称 + 年级 + 方向（web/pwn/re/crypto）+ 一句话签名 + 个人主页/GitHub 链接，按年级分组（25级→17级），成员约 100 人
- **GLORY**：荣誉墙（对应我们的 /honors）
- **Join us**：独立招新注册系统（reg.vidar.club）
- **Wiki**：独立知识库（wiki.vidar.club）
- 设计语言：极简 + 二进制背景点缀 + 大字号，深色/浅色混用
- **借鉴点**：成员卡片信息结构、年级分组展示、个人主页外链模式——与用户"开发部成员主页"构思完全吻合

### 5.2 开源之夏 OSPP / GSoC — "项目招人"模式（开发部项目广场的核心参考）
官网 https://summer.ospp.ac.cn 的**项目列表 → 学生报名**模式：
- 项目详情模板：项目名称 / 描述（背景、已有工作、不足、目标）/ 难度分级 / 技术领域 / 编程语言 / 产出要求 / 技术要求 / 预估工时 / 成果仓库 / 导师
- 流程：社区发布项目 → 学生挑选 → 联系导师沟通 → 提交申请 → 审核 → 入选
- **借鉴点**：开发部"项目广场"可直接复用这个**项目卡片字段模板**（难度/技术栈/人力需求/产出），比自由发挥更专业；"导师-学生"对应"项目负责人-成员认领"

### 5.3 学生社团管理系统（CampusClubs 等开源方案）— 参考但**不采用**
- CampusClubs / Join It / Presence 等：成员管理 + 活动 + 公告
- **结论：不采用**。它们面向"活动型社团"（event-centric），而我们面向"技术协作型"（project-centric）；自建才能贴合网特的多部门多角色 + 公安院校隐私约束

### 5.4 其他战队官网共性
- Nu1L / 0ops / Redbud / 复旦白泽等：官网普遍极简，重点在**荣誉 + 成员 + 招新**三件套
- 多数是静态站——**没人做"登录参与"的协作层**，这是我们的差异化机会

### 5.5 调研结论 → 设计思路
1. **成员主页** = Vidar 卡片结构（头像/昵称/年级/方向/签名/外链）+ 开发部扩展（项目经历列表）
2. **项目广场** = OSPP 项目卡片模板（名称/描述/难度/技术栈/人力需求/负责人/状态）
3. **权限分层** = 静态展示层（参照 Vidar 全公开）+ 协作层（登录后）
4. **招新入口** = 独立于主站的注册流程（参照 Vidar 的 reg. 子域）
